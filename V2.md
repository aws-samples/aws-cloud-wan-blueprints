# AWS Cloud WAN Blueprints v2 — Design

> **Status: implemented.** This document is the authoritative description of the v2 structure and the reasoning behind it. The `infra/` and `policy/` trees are complete and the v1 `patterns/` tree has been removed; `README.md` carries the old-to-new mapping. Where the delivered repository diverges from the design as first written, this document has been corrected to match the repository rather than the reverse — the two notable corrections are the inspection module (section 4) and the example count (section 5).

---

## 1. The problem with v1

v1 is organised as **one directory per use case**, each holding a complete deployable stack in both Terraform and CloudFormation. It produced genuinely good material — the traffic-flow tables and the single-hop inspection matrix are the best Cloud WAN documentation in the repository — but the structure does not scale, for four measurable reasons.

**Adding a use case costs a whole stack.** The 16 pattern directories contain ~48 copies of the same `aws-ia/vpc/aws` module call, 40 CloudFormation templates, and 17 Terraform roots. The infrastructure is ~90% identical; what differs is the network policy. Documenting a routing-policy idea should not require authoring and testing another environment.

**The policy is written two or three times per use case, so it drifts.** Each pattern expresses the same policy as a Terraform data source (or raw JSON), again as embedded YAML in `core_network.yaml`, and a third time as a JSON snippet in the group README. This is not hypothetical: pattern 4 shipped with documentation claiming BGP community `65052:100` while both IaC implementations filtered on `65051:200`.

**The interesting use cases are unbounded and combinatorial.** Cloud WAN's policy surface is segments × sharing × service insertion (2 actions × 2 modes × edge overrides) × routing policies (4 capabilities × 2 directions × 3 association scopes). Directory-per-use-case cannot cover that, and real designs are almost always a *combination* that no single directory represents.

**It is the wrong shape for agents.** A Cloud WAN answer is a policy document. An agent needs composable policy knowledge with declared prerequisites and constraints, not sixteen directories of Terraform from which to reverse-engineer the policy.

### The two observations v2 is built on

**Cloud WAN *is* a single JSON document.** `segments`, `attachment-policies`, `segment-actions`, `network-function-groups`, and `routing-policies` are independent top-level arrays. What differentiates every v1 pattern is that document plus which infrastructure exists for it to attach to. Those are separable.

**Policy capability is a bounded set; use cases are not.** "Use case" is an infinite, arbitrary taxonomy — nobody agrees whether *filter-then-inspect* is one use case or two composed. Cloud WAN's *capabilities* are a closed set defined by the service, and they change only when AWS ships something. Organising around capabilities means the repository's shape is stable and its growth is driven by the service, not by our naming choices.

## 2. The v2 model

Two independent top-level trees.

| | `infra/` | `policy/` |
|---|---|---|
| **What it is** | Deployable infrastructure | Knowledge: what you can express in a policy |
| **Organised by** | Which **attachment types** exist | The policy document's **top-level arrays** |
| **How many** | 5, fixed | 6 capability documents, fixed |
| **Costs money** | Yes | No |
| **Grows when** | AWS adds an attachment type | AWS adds a capability |

They are decoupled. **Inspection does not care whether an attachment is a VPC or a VPN**, so infra patterns are defined purely by what attachments they create, and policy capabilities are documented without reference to any pattern.

The interface between them is the **attachment tagging contract** (section 4), which is uniform across every pattern. That is what lets a policy written while reading `policy/` bind against any `infra/` pattern that has the right attachment types.

### The user journey

1. Read `policy/` to learn what Cloud WAN can express.
2. Assemble a policy for your own requirement — by hand from snippets, or with an agent following `policy/policy_generator.md`.
3. Deploy an `infra/` pattern that has the attachment types your policy needs.
4. Swap your policy in via one variable and test end to end.

Each pattern also ships a **working baseline policy**, so it deploys and forwards traffic before you write anything.

## 3. Structure

```
infra/                                  # deployable infrastructure
├── README.md                           # tagging contract, how to pick, the 2-Region decision
├── 1-basic/                            # VPC attachments only
│   ├── terraform/                      # main.tf, variables.tf, outputs.tf, providers.tf,
│   │                                   #   .header.md, README.md (generated)
│   ├── cloudformation/                 # templates (core_network.yaml GENERATED), Makefile, README.md
│   ├── baseline.json                   # minimal WORKING policy for this pattern
│   └── README.md                       # what it deploys, tags applied, how to test
├── 2-inspection/                       # + inspection VPCs & AWS Network Firewall
├── 3-transit_gateway/                  # + Transit Gateway peered with Cloud WAN
├── 4-hybrid/                           # + Site-to-Site VPN / Connect / Direct Connect gateway
├── 5-multi_account/                    # global + core network + AWS RAM share ONLY
└── tf_modules/                         # compute, firewall_policy, transit_gateway

policy/                                 # what you can express in a policy
├── README.md                           # index, snippet vs example, testability matrix
├── policy_generator.md                 # the workflow for building a policy (humans + agents)
├── 1-core_network_configuration.md
├── 2-segments.md
├── 3-attachment_policies.md
├── 4-segment_sharing.md
├── 5-service_insertion.md
├── 6-routing_policies.md
└── examples/*.json                     # rare, complete, validated, deployable policies

tools/
├── validate_policy.py                  # schema + cross-reference + Cloud WAN constraint checks
└── sync_cfn_policy.py                  # baseline.json -> CloudFormation template (+ --check)

SKILLS.md                               # single agent entry point
CONVENTIONS.md · CONTRIBUTING.md · README.md · blueprint.yaml · V2.md
```

`infra/` and `policy/` sit at the **root, separated**, rather than nested under a shared parent. The reason is that it makes the central design decision self-evident from the tree: two top-level directories say "infrastructure and policy are independent", where a shared parent would quietly imply they are two facets of one thing. Nesting would also not have preserved any inbound link — v1 links point at `patterns/<group>/<pattern>/terraform`, which changes under any restructure. The word "patterns" survives as repository vocabulary in `README.md`, which indexes both trees.

## 4. `infra/` — five patterns

A pattern is defined by **which attachment types exist**. Nothing else.

| Pattern | Adds | Its baseline policy demonstrates |
|---|---|---|
| `1-basic` | Spoke VPCs | Segmentation and tag-based association |
| `2-inspection` | Inspection VPCs + AWS Network Firewall | A network function group with traffic actually flowing through it |
| `3-transit_gateway` | Per-Region Transit Gateway peered with Cloud WAN | Transit Gateway route-table attachments |
| `4-hybrid` | Site-to-Site VPN / Connect / Direct Connect gateway, each optional | Attachment-**type** based association |
| `5-multi_account` | Global network + core network + RAM share, **no VPCs** | Sharing a core network, and the limitations that follow |

### Two Regions, always

Every pattern deploys **`us-east-1` and `eu-west-1`**. Extending to three or more Regions is a documented local change to the infra code (more provider aliases, more VPC module blocks); the policy follows without restructuring, because Cloud WAN segments are global.

This is a deliberate trade. It buys a static edge-location list, which is what makes a single policy file serve both IaC tools (section 6), and it keeps the provider ladder short — Terraform still has no `for_each` on provider blocks, so every Region costs a literal `provider` alias.

**What it costs:** v1's single-hop inspection matrix used four Regions, and at two Regions single-hop and dual-hop look nearly identical in practice. The mitigation is the snippet/example split working as designed — `5-service_insertion.md` shows the full four-Region `with-edge-overrides` matrix as a snippet and states what you would extend to observe it live. This is the one real loss in v2 and it is accepted knowingly.

### The attachment tagging contract

Uniform across every pattern, documented in `infra/README.md`:

| Tag | Applied to | Purpose |
|---|---|---|
| `domain = <segment>` | VPC and Transit Gateway route-table attachments | Associate to the segment named by the tag value |
| `inspection = true` | Inspection VPC attachments | Add to the inspection network function group |

Hybrid attachments carry **no tag**. They are matched on `attachment-type` (`site-to-site-vpn`, `connect`, `direct-connect-gateway`). This is deliberate pedagogy rather than an omission: it lets `3-attachment_policies.md` teach both binding methods and when each is correct — tags for intent you choose at resource-creation time, attachment type where the type *is* the intent.

Each pattern's README states which tags it applies, and that changing them is a local code edit.

### Inspection: what was designed, and what shipped

The design called for the inspection layer to be a shared module (`infra/tf_modules/inspection/`) that patterns 3 and 4 could include, so that Transit-Gateway-plus-inspection was a composition rather than another pattern.

**That is not what shipped, and the reason matters.** In Terraform, the inspection VPC is not ours to modularise: it is created by the upstream `aws-ia/cloudwan` module as a central VPC of type `egress_with_inspection`, which also owns the routing and the core network attachment. Wrapping that in a local module would have added a layer that forwards variables and owns no logic. What is genuinely reusable is the AWS Network Firewall policy, and that *is* a shared module — `infra/tf_modules/firewall_policy/`, used twice by `2-inspection`, once per Region.

So inspection ships as a pattern only, and adding it to `3-transit_gateway` or `4-hybrid` is a documented local change (one more `aws-ia/cloudwan` central VPC block plus a `firewall_policy` module call) rather than a shipped composition.

The design's underlying claim still holds and is what keeps the pattern count at five: inspection is indifferent to attachment type, so `policy/5-service_insertion.md` documents it once, against no pattern in particular. `2-inspection` exists as the simplest place to *learn* the capability, not because inspection belongs to VPC attachments.

### `4-hybrid` stays consolidated

Splitting VPN, SD-WAN/Connect, and Direct Connect gateway into three patterns would create three directories differing only in which BGP-capable attachment they create — a distinction every policy capability ignores. The real difference between them is **prerequisites**, not policy behaviour, so each sub-type is independently optional and the README states what you need to test it: Direct Connect gateway needs a real circuit, VPN can be driven by a software router, Connect needs an underlay VPC plus an appliance.

### `5-multi_account` is deliberately minimal

Global network, core network, RAM share. No workloads. Its README carries the limitations discussion, and the substantive one is that **attachment tags are set by the attachment owner** — so in a shared core network the segment a VPC lands in depends on a tag controlled by another account. That is why `require-attachment-acceptance` and defensive attachment-policy design matter far more here than in a single account.

## 5. `policy/` — six capability documents, snippet-first

Flat, one document per subsection, mirroring the policy document's top-level areas so a reader (or an agent) knows exactly which part of the JSON each one produces.

| Document | Produces |
|---|---|
| `1-core_network_configuration.md` | `core-network-configuration` |
| `2-segments.md` | `segments` |
| `3-attachment_policies.md` | `attachment-policies` |
| `4-segment_sharing.md` | `segment-actions` (`share`) |
| `5-service_insertion.md` | `network-function-groups` + `segment-actions` (`send-to`, `send-via`) |
| `6-routing_policies.md` | `routing-policies` + `attachment-routing-policy-rules` |

Segments and attachment policies are **separate** documents despite always being authored together. The 1:1 mapping with the policy document is the organizing principle, and attachment policies — rule numbering, condition types, evaluation order, association methods — are where users most often get stuck, so they get their own room.

Each document explains the capability and its options, going beyond the AWS documentation, with snippets inline next to the prose that explains them.

### Snippet versus example

- **Snippet** — a *fragment*: one array element, or one array. Illustrative, not deployable on its own. Lives **inline** in the markdown.
- **Example** — a *complete, valid* policy document, deployable against a named infra pattern, validated in CI. Lives in `policy/examples/`.

CI extracts every fenced ` ```json ` block from `policy/*.md` and schema-validates it as a fragment, so inline snippets cannot rot the way v1's embedded policies did.

### Example admission rule

Snippets are the default. An example is justified only if **all four** hold:

1. It cannot be understood from the snippets alone — the value is in the *interaction* between two or more capabilities.
2. It is deployable end to end against a named infra pattern, so it can be verified rather than merely read.
3. It produces a routing outcome that is non-obvious, or that is easy to get wrong when composing the snippets by hand.
4. It does **not** differ from an existing example only by parameter values (CIDRs, Region names, segment names, community values). Parameterisation is not novelty.

`policy/README.md` lists every example with a one-line *"why this earns its place"*. If you cannot write that sentence, it is a snippet. The enforceable version lives in `CONVENTIONS.md` and is checked in review.

Applied to v1's 16 patterns, the rule was expected to admit roughly three. **Applied honestly, it admitted one.** `policy/examples/filter_then_inspect.json` is the only example in the repository.

The two candidates that were expected to clear it did not, and both failed on criterion 2 — deployable against a *named* pattern:

- **Transit Gateway with service insertion.** No shipped pattern has both a Transit Gateway and an inspection VPC (see section 4), so this cannot be deployed without an infra code change. It is a snippet in `5-service_insertion.md`.
- **Summarization.** The per-Region Direct Connect gateway reasoning is genuinely non-obvious, which satisfies criterion 3 — but observing it requires a real Direct Connect circuit and a BGP peer, which `4-hybrid` cannot provision for you. It is a snippet in `6-routing_policies.md`, with the prefix lists shipped in `4-hybrid` so the infra half is real.

`policy/README.md` records every rejected candidate with its reason, which is more useful than the examples directory would have been: it tells a contributor proposing an example exactly which bar their candidate has to clear.

The 1/16 outcome is reported rather than corrected. A gate that admits what you predicted is not a gate.

### `policy_generator.md`

The workflow for turning a stated requirement into a policy document: the intake questions, the assembly order (which is just the 1→6 document order), the constraint checklist, how to validate, and what to hand back — the policy JSON, which infra pattern to deploy, and the residual steps a policy cannot express (appliance mode on the inspection VPC, prefix lists in `us-west-2`, on-premises BGP configuration).

It is deliberately **separate from `SKILLS.md`**. `SKILLS.md` is the stable artifact you would lift into another agent's context; the generation procedure is a workflow that changes whenever the repository's structure or tooling changes. Keeping them apart means tooling changes do not edit the service reference.

### Testability matrix

`policy/README.md` carries a matrix framed as **testability**, not capability coupling: *"to exercise summarization end to end you need a BGP-capable attachment, which patterns 3 and 4 provide."* The capability itself is documented independently of any pattern.

## 6. One policy document, both IaC tools

Each pattern's `baseline.json` is canonical and is a **working** policy, not a placeholder — for `2-inspection` that means it actually inserts the inspection VPC into the traffic path, or the firewall would sit idle and the pattern could not be verified.

- **Terraform** reads it with `file(var.policy_document)`, defaulting to the pattern's baseline. No HCL data source, so no second authoring.
- **CloudFormation** cannot take a document this size as a stack parameter (parameters cap at 4096 characters), so `cloudformation/core_network.yaml` is **generated** from `baseline.json` by `tools/sync_cfn_policy.py`, with a CI drift check — the same generate-plus-check shape already used for the terraform-docs READMEs.

Fixing the Region count at two is what makes this safe: the edge-location list is static, so one file genuinely serves both tools. This eliminates the drift class that produced the v1 pattern-4 bug.

Users override with one variable:

```bash
cd infra/2-inspection/terraform
terraform apply -var policy_document=../../../my-policy.json
```

The baseline's `attachment-policies` block is the stable part — the binding. Users extend `segment-actions` and `routing-policies`; they do not rewrite the binding.

## 7. Validation

Three gates, cheapest first. This is what makes it defensible for an agent to emit a policy.

**Gate 1 — schema.** `tools/validate_policy.py` validates document shape: known keys, types, enums (`send-to` | `send-via`, `dual-hop` | `single-hop`, `inbound` | `outbound`), required fields.

**Gate 2 — cross-reference and Cloud WAN constraints.** Schema validity is not policy validity. These encode the limitations that actually break designs:

| # | Check |
|---|-------|
| 1 | Every segment named by a segment action or attachment policy is declared |
| 2 | Every network function group named by a service-insertion action is declared |
| 3 | Rule numbers unique within each numbered array; `allow` rules precede catch-all `drop` |
| 4 | Every Region in `with-edge-overrides` is a declared edge location |
| 5 | Every routing policy name referenced is declared; routing-policy numbers unique |
| 6 | ASNs in routing policies do not overlap the core network `asn-ranges` |
| 7 | No routing policy is associated with a network function group (**unsupported**) |
| 8 | Segment is `isolate-attachments: true` where intra-segment `send-via` inspection is intended |
| 9 | `dual-hop` used only where inspection exists in every participating Region |
| 10 | `summarize` actions are `outbound` only, and only on BGP-capable attachment labels |
| 11 | No BGP-community match or set on Direct Connect or Transit Gateway peering attachments |
| 12 | No BGP attribute modification targeted at VPC attachments |
| 13 | Prefix lists referenced by routing policies are declared as created in `us-west-2` |
| 14 | Every tag the chosen infra pattern applies is matched by some attachment-policy rule |

Checks 6–13 each correspond to a documented Cloud WAN limitation, not invented lint. Check 14 catches the failure mode where attachments silently never associate, which is the most common Cloud WAN support issue and one v1 could only surface by deploying.

**Gate 3 — the service.** Cloud WAN validates a policy when you create a **policy version** and produces a **change set** you must explicitly execute; nothing changes until you do. That is an effective dry run and is the recommended final gate for anything destined for a real network. Documented as a local command, not a CI job — CI stays static and credential-free.

## 8. What a contribution costs

| Change | Cost |
|---|---|
| New use case, no new capability | A paragraph and a snippet in an existing `policy/*.md` |
| New use case clearing the four-part rule | The above, plus one validated JSON in `policy/examples/` |
| New service capability | A new `policy/N-*.md` |
| New attachment type | A new `infra/` pattern, or a new optional sub-type in `4-hybrid` |
| New Region in a pattern | A provider alias and a module block, locally |

The common case — a new use case — costs a paragraph. That is the point of the restructure.

## 9. How the migration was done

The new trees were built **alongside** `patterns/` rather than by moving it, and `patterns/` was deleted only in the final step. This kept CI green throughout, and let the shape be reviewed on one pattern before the other four were ported.

Two things were worth the cost of doing it this way. First, `infra/1-basic` could be compared directly against v1 pattern 1 while both existed, which is how the ~13 v1 bug fixes made in the preceding phase were confirmed to have carried into v2 rather than being silently dropped. Second, the validator was written against real baselines as they were built, and each new pattern found bugs in it — six validator defects in total, every one of which would have let a broken policy pass — including a tag-block regex that stopped at the first `}` (usually inside a `${...}` interpolation in a tag *value*), silently hiding every tag declared after it.

| Step | Work | Gate |
|---|---|---|
| 1 | `infra/` + `policy/` skeletons, `tools/`, CI extension, `blueprint.yaml`, `CONVENTIONS.md` | Repo-wide checks stay green |
| 2 | `infra/1-basic` ported end to end from v1 pattern 1 | Deploys; `baseline.json` passes gates 1–2; CFN template matches `baseline.json` |
| 3 | `policy/` content: the six capability documents, harvested from the v1 group READMEs | Every inline snippet schema-validates |
| 4 | `infra/2-inspection`, `3-transit_gateway` | as step 2 |
| 5 | `infra/4-hybrid`, `5-multi_account` | as step 2 |
| 6 | `policy/examples/` — those that clear the rule (one did) | Each validates and names its pattern |
| 7 | `SKILLS.md` part two, `policy_generator.md` content | An agent can answer a novel requirement with a validated policy |
| 8 | Delete `patterns/`; add the old→new mapping table to `README.md` | No broken internal links |
